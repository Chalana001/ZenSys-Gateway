## The three findings worth keeping

**1. A context value written by an inner handler cannot travel outward — again.** The
access-log test failed because the log line had no `service` field. `authenticate` derived
a context; `AccessLog` sits *outside* it. This is the identical failure M4's `RequestState`
was created for, and it was found the same way (a test, not reasoning). The fix: a second
slot installed by `RequestState`, and `authenticate` writes into it instead of deriving.

**2. The catch-all that gives the JSON error contract suppresses ServeMux's own 405.**
Probed empirically with a standalone program: with `/internal/v1/` registered,
`POST /tenant-routes/{slug}` returns 404 instead of 405 with an `Allow` header. Fix: derive
both the routes *and* the `Allow` values from one `endpoint` table, and register a
path-only mux to answer "does this path exist for any method?". `ErrMethodNotAllowed` is
the one addition to §69's closed error-code set.

**3. The probe was measuring the wrong thing twice, and both were its own bugs.** The F
config was derived from A *after* A had rewritten `route_ttl`, so the substitution silently
stopped matching; and section F ran after section D, which deliberately stops the POS
upstreams, so three assertions reported 502. Both were found by the harness, not by
reading it.

## Decisions taken

- **Tokens are compared as SHA-256 digests**, not raw strings: `subtle.ConstantTimeCompare`
  returns 0 immediately on a length mismatch, which leaks the stored token's length. Hashing
  makes every comparison 32 bytes and keeps the raw secret off the long-lived heap.
- **The comparison loop is branch-free** (`idx = eq*(i-idx) + idx`), and a behavioural test
  asserts the *last* duplicate wins — the only available proof that the loop ran to
  completion. Duplicates are rejected at construction, so it is unobservable in production.
- **`ErrInvalidTransition` is unreachable through the API.** Every state can move to both
  ACTIVE and DISABLED, so no request can produce an illegal transition. Tested at the
  mapping with a stub lifecycle, and stated in the plan rather than left as a gap.
- **`GET /tenant-routes` is narrowed to the caller's products**, and a single-product caller
  is narrowed without asking. Stricter than §42 requires; documented as such.
- **A known consequence, documented not deviated from:** authorizing `disable`/`release`
  against the *stored* product means a single-product service can enumerate the other
  product's tenants by guessing slugs (404 vs 403). Both callers are the platform's own
  services on a loopback listener, and the plan specifies exactly these statuses. Candidate
  for tightening in M7.
- **`release` checks `confirm` before reading the registry** — a disclosure property, not an
  optimisation. A test pins the ordering.
